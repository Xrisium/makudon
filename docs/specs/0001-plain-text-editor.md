- 调试约定：[有真机时仅用真机，无真机才用模拟器，用户明确指定除外](../device-policy.md)。
- 关联：[数据安全约定](../data-safety.md)、[验收规范](../testing/plain-text-editor-acceptance.md)。

## 1. 切片目标与范围

用户能新建或导入纯文本 / `.md` 文稿，**同一时刻编辑一篇**，输入、选择、复制粘贴、删除与撤销，看到准确的保存状态；正常退出或进程重启后继续写；保存失败时仍可保留当前编辑内容、重试和恢复已提交版本。多个私有副本需保留并可重新打开，不扩展为目录系统。

最短流程：新建 / 系统选择器导入 / 文件管理器“用 Makudon 打开” → 建立独立私有文稿 → 编辑 → 自动保存 → 重开继续 / 导出 `.txt` 副本。用户本轮要求启动默认进入最近列表，由列表打开文稿；已实现外部关联时可直接进入新导入副本。最小列表可回到旧稿，新建与导入均不覆盖任何已有文稿。

2026-10-24 界面讨论已取消常规手动保存按钮，保留异常重试和离开前保存屏障。完整三标签、目录及 Markdown 双视图属于后续整体设计，见[界面方案](0003-workspace-and-markdown-views.md)，不自动并入本片。

| 本片范围 | 后续另做 |
| --- | --- |
| 单活动编辑器、新建 / 导入的独立文稿、最小重新打开列表 | 标题重命名、目录树、搜索、标签、排序配置 |
| 中文输入、选区、复制粘贴、会话内撤销 / 重做 | Markdown 工具栏、语法高亮、预览、富文本 |
| 本地全自动保存、错误反馈与重试、上一提交版本恢复 | 历史版本浏览、无限撤销、跨设备同步 |
| 本机纯文本 / `.md` 导入副本、系统打开关联、SAF 创建 `.txt` 导出副本 | 外部文件持续编辑、批量导入、ZIP 备份 / 恢复 |

本片可展示给用户试用，但在导出出口完成前仅用合成文本。不要将“文件在应用内”描述为已有备份。

## 2. 正文格式与持久化范围

- 正文是标准 UTF-8、无 BOM 的 `.txt` / `.md`，不嵌入 JSON、数据库或自定义文件头。新稿默认 plain；导入 Markdown 保留其类型与源码，本片不渲染。
- 应用内换行统一 LF；粘贴时将 CRLF / CR 映射为 LF。不得 trim、改缩进、吞空行或自动追加末尾换行。
- 中文、emoji、组合字符和制表符原样保留；不做 Unicode 归一化。空字符串是合法的 0 字节文稿，必须与读取失败区分。
- UTF-8 编解码严格报告非法序列，不用替代字符把损坏或非法编码伪装为成功。导入可移除 UTF-8 BOM 并规范换行，不自动猜测 GBK / UTF-16；具体边界见 [导入设计](0002-import-and-file-association.md)。
- 首片已确定支持基线：10 万 Unicode 码点，且 UTF-8 大小 ≤ 1 MiB，两项同时满足。UTF-16 `String.length` 不能直接当作这个字数指标；该基线尚未实测达标。
- 超限粘贴拒绝整个编辑操作并解释，不截取前半段；磁盘中遇到超限正文进入保护状态，不能截断后回写。拒绝后的原文、选区和组合输入不能损坏。
- 正文落磁盘；光标 / 选区 / 滚动位置只作为小量 UI 状态，恢复时做范围校验。完整长正文不放进 Bundle、`SavedStateHandle` 或 `rememberSaveable`。
- 正常 Activity 重建应尽量保持选区、滚动与会话内撤销；进程死亡后只保证恢复已提交正文，不保证撤销栈、输入法候选或精确滚动位置。按 Android 官方建议，长期内容依靠[本地持久化](https://developer.android.com/topic/libraries/architecture/saving-states)。

## 3. 最小结构与依赖

继续单 `:app` 模块，按需要增加 `feature/editor` 与少量 `data` 实现。下面是职责，不要求按每一行分别造类或接口。

| 职责 | 边界 |
| --- | --- |
| EditorScreen / 文本输入状态 | 展示正文、选区、IME composition、保存状态和操作；不直接碰文件 |
| EditorViewModel | 协调打开、编辑动作、保存状态与离开请求；不把保存回执写回文本框 |
| 保存协调器 | 管理正文版本、调度、单写者队列和保存屏障；核心规则可用虚拟时钟测试 |
| 私有文件适配器 | 原子写入、回读验证、加载、保留上一版本；所有 I/O 在后台 |
| 导入 / 外部打开适配器 | 只读源 URI、有界校验、独立副本发布；外部 Intent 不直接进入保存 writer |
| 应用装配 | 手动构造依赖；同一进程的同一文稿只有一个存储所有者和写入队列 |

编辑状态可以使用 Compose 类型并留在 UI 层；domain / 保存规则只接收不可变正文快照，不依赖 Context / Android Uri / Compose。无需 Hilt、Room、DataStore、多模块或通用存储插件框架。

未来实现时只为实际 ViewModel、生命周期、协程与平台测试增加所需的显式依赖，并核对现有 BOM/API；本轮不选新版本、不改依赖。优先评估现有稳定 `BasicTextField` 的状态式 API；若当前版本不具备所需的组合输入 / 撤销能力，先给出验证结果和替代方案，不为了追逐新文档示例自动升级工具链。

## 4. 输入行为

- 全屏多行编辑，控件自己管理文本滚动；避免外层和文本框出现互相抢手势的双重纵向滚动。
- 正文变化即时显示；保存异步完成不能设置文本框正文、重建输入状态、移动光标或中断中文候选。
- 只改选区 / 光标 / composition 元数据不触发正文保存；正文确实改变才生成新的会话版本。
- 自动保存可记录当前文本缓冲区中的组合输入文字，但不主动结束 composition。候选最终上屏会形成更新版本；若进程在选词前死亡，不承诺恢复候选面板，恢复出的文本可能仍含上次落盘的临时拼音。
- 会话内撤销 / 重做针对编辑动作，不把自动保存当作新编辑，不跨进程持久化撤销历史。
- 系统返回优先由输入法收起键盘；真正离开编辑界面时按第 6 节保存屏障处理。键盘展开时当前输入行、保存状态和必要操作仍可触达。
- 支持系统字体缩放、深浅色、旋转、TalkBack 和至少 48dp 操作目标。首片不提供复杂字体面板。

输入控件建议依据 [Compose 官方输入文档](https://developer.android.com/develop/ui/compose/text/user-input)，但是否满足当前工程和真实输入法要求须在实施第一步验证。

## 5. 保存状态与版本

版本号是**当前进程会话内**的单调计数，不是磁盘格式，也不靠设备时间排序。加载成功后以已读正文建立版本 0；每次正文变化增加版本。选区变化不增加正文版本。

| 状态 / 文案方向 | 条件与可执行操作 |
| --- | --- |
| 正在打开 | 禁止编辑，不能在读取返回前用空文本启动自动保存 |
| 等待保存 | 当前版本尚未提交；可继续输入，按自动调度提交，无常规保存按钮 |
| 正在保存 | 某一快照正在写；输入继续，更新只合并到待保存快照 |
| 已保存到本机 | **当前正文版本**与最后确认提交版本一致，且没有未解决的写入 / 读取错误 |
| 保存失败，修改尚未保存 | 保留编辑缓冲区和旧文件；展示可理解原因与“重试”，可尝试导出当前内容 |
| 无法打开 / 需要恢复 | 不用空文稿替代；保留已有文件，提供重试、查看恢复副本等动作 |

“已保存到本机”和“已导出副本”分开表示。状态不能只依赖颜色、Toast、修改时间或“协程已启动”。文件损坏 / 回读失败时不显示“已保存”。

### 单写者与旧回执

1. 同一文稿的加载、保存、恢复通过同一所有者按文稿 ID 串行协调，不允许并发调用原子文件写入。Activity 重建、关联打开或多个窗口不得各自创建一套 writer；本片不支持多个独立编辑会话。旧稿回执不能改变新稿正文、状态或目标路径。
2. 每次保存请求在一致的 UI 状态点捕获正文与版本；磁盘 writer 只接收不可变快照。最多一个正在写、一个可替换的最新待写快照，不无限排队每个按键。
3. 新输入不能取消已经开始的文件事务。可以替换尚未开始的待写快照，禁止用 `collectLatest` 直接取消正在提交的 I/O。
4. 例如版本 10 正在写时用户编辑成 11：10 成功只确认 10，当前 UI 仍是待保存 / 正在保存，不能显示 11 已保存；然后写最新的 11 或更高版本。回执从不覆盖当前正文。
5. 同版本重复请求不重复轮换恢复副本；正文与已提交内容完全一致时可复用该已确认结果，不额外写文件。即使做去重，先前失败状态也必须经过明确核对才能解除。

## 6. 全自动保存、异常重试与生命周期

建议参数是工程起点，尚未测量：

| 触发 | 调度规则 |
| --- | --- |
| 停止输入 | 正文变化后 500 ms 没有新变化，请求保存最新快照 |
| 持续输入 | 从最早尚未覆盖的修改开始计时，最长 2 s 请求一次最新快照；后续按键不能无限重置此期限 |
| 失败后“重试” | 不等待 debounce，创建捕获版本的保存屏障；若已有写入，等待它完成再处理最新目标；这不是常规手动保存入口 |
| 用户主动离开编辑界面 | 请求最新正文保存；成功且没有更新版本后再离开。失败时留在编辑界面，允许重试、继续编辑或明确确认放弃未保存部分 |
| Home / 切其他应用 / 锁屏 | 尽早请求一次立即保存，仍在后台 I/O 执行；不能阻止系统离开，也不能保证系统会给足执行时间 |

“重试完成”只确认点击时捕获的版本，或包含其后编辑的更高版本；若用户又输入，UI 必须显示还有修改。离开流程不能只等旧版本保存成功便关闭新编辑。无保存按钮不改变当前版本校验、保存屏障与生命周期规则，也不承诺异常时未落盘文字零丢失。

正常 I/O 下的初始验收目标：提交完成耗时 p95 ≤ 1 s，因此停止输入后通常在 1.5 s 内变为已保存，持续输入通常在最早未覆盖修改后的 3 s 内得到覆盖。统计须包含恢复副本、同步、提交与回读，**不能把 2 s 调度周期说成磁盘故障时最多丢 2 s 的保证**。性能不达标时先分析、调校或缩小支持范围，再交付，不擅自降低可靠性步骤。

保存队列的生命周期由进程内单一所有者管理；不能因为页面停止收集状态或 Activity 旋转就取消正在写的事务，也不创建脱离管理的永久后台任务。退出后的尽力保存不依赖 WorkManager、前台服务或网络。

不阻塞主线程，不在 `onPause` 同步写大文件，不依赖 `onDestroy` / `onSaveInstanceState` 最后抢救全文；系统可能直接结束进程。参见 [Activity 生命周期](https://developer.android.com/guide/components/activities/activity-lifecycle)。

## 7. 私有文件提交与上一版本

由于已纳入导入与关联打开，每篇使用独立 ID，不使用会覆盖旧稿的固定单槽。自动保存的最小布局如下；完整初始化与元数据约束见 [导入设计第 5 节](0002-import-and-file-association.md)。

```text
filesDir/documents/<document-id>/
  metadata.json     少量静态元数据，不包含正文
  body.txt          权威正文；Markdown 文稿使用 body.md
  previous.txt      最近一次提交前的正文，有限恢复副本
```

正文与 previous 分别通过平台 `AtomicFile` 操作；静态元数据在新建 / 导入发布时初始化，普通自动保存不重写它。原子文件自身的临时 / 兼容备份文件不是用户版本历史，不用时间戳来猜哪个最新。Android 官方明确要求调用者自己保证 [AtomicFile 的线程互斥与写入完成流程](https://developer.android.com/reference/android/util/AtomicFile)。下文的 body 指该稿实际 body.txt 或 body.md。

### 初始化

新建一律生成新 ID，通过暂存初始化正文与元数据、验证后发布，再进入编辑。已有文稿从有效目录加载；任何已存在目录或异常痕迹都不能因加载失败而被当作新建空稿覆盖。初始化失败明确重试，不能显示为“已保存”。

目录已存在但正文缺失，或只剩中断写入痕迹，属于打开 / 恢复流程，不能当成首次空白文稿覆盖。初始空文稿不一定已有 previous，属于合法情况。

### 一次提交的必要步骤

1. 捕获目标快照；按第 2 节规则编码。保留当前已确认正文在内存中的基线，供本次恢复副本使用。
2. 若存在旧基线且与目标不同，先原子更新 `previous.txt` 为**旧的已确认正文**，同步并回读验证；失败则停止本次主文件写入，旧正文保持可用。
3. 对当前文稿的 body 文件开始原子写入，完整写入快照，显式检查写入 / `FileDescriptor.sync()` 的异常，再按平台契约完成提交。提交后的原子读取必须与目标字节一致，才确认保存成功。
4. 回读或提交结果不确定时报告失败 / 待核对，保留所有现存可恢复文件和内存新内容，不依据“方法返回了”或文件存在就更新已保存标志。再次尝试前先串行核对当前文件是旧基线还是目标快照。
5. 成功后推进已确认版本与内存基线；若当前正文已有更新版本，立即按调度处理最新待写内容。

这些是**两次独立原子提交**，不宣称两份文件组成事务。中间中断时，previous 可能与旧主文件相同；这是允许的。主文件成功时 previous 至少保留它的前一个确认基线。启动时不能仅因 previous 较新 / 较旧而自动改用它。

使用 `startWrite` 返回的流时遵循 `finishWrite` / `failWrite` 契约，不能当成普通 `use` 关闭就算提交。取消、清理和提交完成阶段需要明确标记；不能在事务已经提交后执行会删掉有效结果的错误回滚。保存事务一旦开始应完整收尾，再响应后续请求。

全量回读和有限双副本增加 I/O，首片以支持范围内实测换取简单的完整性判断；不是日志型编辑引擎、每键 fsync 或无限版本历史。也不承诺能检测落盘很久以后仍合法 UTF-8 的任意内容篡改；当前未设计持久内容校验清单。

## 8. 失败与恢复规则

| 情况 | 必须行为 |
| --- | --- |
| 容量不足、写入 / sync 失败 | 保留原主文件、可用 previous、当前编辑缓冲区；状态为失败，不用空文本替代，不无限高速重试 |
| 保存失败后继续输入 | 更新内存最新快照；失败状态保持可见，后续自动提交暂停，待用户点重试；防止错误风暴 |
| 用户重试 / 重新进前台 | “重试”立即尝试最新内容；重新进前台仅提示错误与检查状态，不自行清除错误或覆盖文件 |
| 正在写入时杀进程 | 下次通过原子文件读取语义打开已完成的主版本；若新提交已完成，可恢复新版本；否则保留此前完整版本，不能出现截断的混合文本 |
| 提交后、UI 收到回执前杀进程 | 重启以磁盘完整正文为准；不根据旧的内存状态回滚 |
| 正文缺失、读取异常、非法 UTF-8、超限 | 进入保护状态，不启动自动保存，不“修复”为零字节；允许重试或检查 previous |
| previous 有效，主文件失败 | 提供只读查看与“用此版本恢复”；说明是较早保存版本，需要用户明确操作，不能静默回退后显示最新已保存 |
| 两份均不可读 | 保留文件与错误分类，阻止破坏性写入；只能重试或后续受控恢复，不能承诺必能找回 |
| 用户选择恢复上一版本 | 先保存现有主文件及其异常痕迹为独立恢复材料，失败则不改原文件；再写入选择的完整副本。不能先把坏正文轮换进 previous |

恢复动作只在需要时创建 `recovery/<唯一标识>/` 保存现场；不每次输入生成无上限历史。恢复材料不自动清除，后续清理策略需要另行设计。存储不足无法保护现场时，允许只读查看或另存副本，不强行替换。

`previous.txt` 仅保护一个提交前版本，可能只是几秒前，不能替代撤销、历史备份或恢复全部误删。正常主文件也可通过菜单查看上一保存版本；恢复要确认，不能被下一次自动保存立即覆盖现场。

进程在失败后结束会丢失仅在内存中的修改；文案必须明确区分“仍在当前界面”和“已经持久化”。可尝试把内存内容导出副本，但导出也可能失败。

## 9. 最小导出（已纳入首片）

2026-10-31 交互扩展见 [ADR 0007](../adr/0007-file-manager-first.md)：固定内容 / 文件名快照后选择导出方式，增加 FileProvider 分享与 API 29+ 下载目录保存；下面 CREATE_DOCUMENT 仍保留为系统保存位置后备。分享启动不表示外部保存成功，外部选择取消 / 写入失败可在当前面板重试，关闭面板后可生成新的快照。

- 操作名为“导出 .txt 副本”，使用 `ACTION_CREATE_DOCUMENT`、`text/plain`，按文稿显示名建议 `.txt` 文件名；无名称时为 `未命名文稿.txt`，不请求广泛存储权限。`.md` 文稿在本片也导出 `.txt`，Markdown 字符仍是普通正文，之后可由用户重命名扩展名。
- 点击时捕获当前正文快照，包含尚未自动保存的输入；写入的是这个快照，不在 picker 返回时偷偷换成另一个版本。保存在内存的导出目标与正文版本关联，picker 期间进程死亡不假装继续或成功。
- 提供取消、写入中、失败和完成反馈；流写入并成功关闭后才报告“副本已写入所选位置”。有读取权限且 provider 支持时回读核对；结果不确定时明确提示检查文件。
- 导出不能把主文稿标为已保存、不能清除主存储失败、不能建立外部持续同步关系。导出后继续输入，副本自然不是最新版本。
- 不覆盖已有文档；系统创建文档的重名处理不能被解释为应用主动覆盖成功。取消不得改主文稿或其保存状态。
- 若写入中断，目标可能已出现空 / 不完整文件；提示实际结果，用户可在所选位置检查，不擅自删除其他文件或抹除私有原稿。
- 云盘 provider 关闭流成功不代表云端传输完成；本片先在本地 provider 验收，不宣称自动同步或异地备份成功。

系统创建文档与重名行为见 [SAF 官方指南](https://developer.android.com/training/data-storage/shared/documents-files)。

## 10. 可保证与不可保证的范围

| 事件 | 首片保障目标 |
| --- | --- |
| 已显示当前版本“已保存到本机”后，应用进程被结束 / 正常重启 | 完整恢复该版本或更新的已提交版本 |
| 最新版本正在等待 / 写入时进程被结束 | 完整恢复最后完成提交的版本；未完成输入不作零丢失承诺 |
| 普通写入失败且进程仍存活 | 旧的已提交正文可用，新内容留在当前编辑缓冲区，错误可见并能重试 |
| 后台 / 锁屏 | 尽力立即提交；不等同于已完成，不能以回调已发生来证明 |
| Activity 旋转重建 | 不丢当前会话正文，不开第二个 writer，不中断正常保存队列 |
| 突然断电、文件系统损坏、闪存故障 | 不承诺已保存版本绝对不丢；原子提交与同步降低风险，需实际设备验证，不以进程测试代替 |
| 卸载、清数据、设备丢失 | 私有主文件和本地恢复副本均不能保护；需已完成的独立导出 / 外部备份 |

## 11. 最初候选实施顺序（历史记录，当前已获整体实施授权）

1. **输入体验验证**：限定现有工具链和合成正文，验证控件、composition、撤销与已确定的 10 万码点 / 1 MiB 基线，按设备约定优先使用已连接真机。验证不达标先调整方案，不继续接存储掩盖问题。
2. **保存规则与文件边界**：实现最少职责、虚拟时钟 / 延迟 writer 测试、原子提交与故障注入；先证明旧回执不假报成功和失败不截断原稿。
3. **接入活动文稿 UI**：按独立文稿 ID 打开 / 初始化、默认最近列表、全自动保存、异常重试、生命周期与切换保护；提供可复现的目标设备测试交付。
4. **恢复与文件出入口**：上一版本查看 / 确认恢复、本机文件导入副本、系统打开关联和最小 `.txt` 导出，按 [导入协议](0002-import-and-file-association.md) 保证旧稿与源文件不受破坏。未完成约定范围不标为切片完成。
5. **完整验收**：执行 [验收规范](../testing/plain-text-editor-acceptance.md)，记录设备、输入法、APK 身份、全部失败项与未覆盖项；用户亲自试用后再安排文稿管理。

整个设计不要求立即一次性实现上述所有步骤；用户可逐步发出任务。业务测试、平台测试和测试钩子均属于未来实现，本轮只定义要求。
